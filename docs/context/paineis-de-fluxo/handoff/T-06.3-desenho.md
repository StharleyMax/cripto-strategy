### 1.2 A causa, com EXPLAIN

`_SELECT_EXTENT_SQL` (`infra/postgres_series_window_reader.py:49-52`) é
`SELECT MIN(bucket_end), MAX(bucket_end) … WHERE series_key_id=%s AND symbol=%s`.

O planner o reescreve como `LIMIT 1` ordenado sobre `series_bucket_end_idx (bucket_end DESC)`, e o filtro de
`series_key_id`/`symbol` fica **fora** do índice. Uma série que nasceu tarde obriga então a varrer, do chunk mais
antigo para a frente, **todas as linhas de todas as outras séries** até achar a primeira dela:

```
EXPLAIN (ANALYZE, BUFFERS) … series_key_id='bc0b8a78…' AND symbol='BTCUSDT'
-- Rows Removed by Filter: 106.842 + 215.591 + 241.920×9 + 582.947 + 763.691 …
-- Buffers: shared hit=1.167.407 · Execution Time: 1.061 ms
```

`[MEDIDO]`. As 4 séries que nasceram tarde custam 1.107 / 944 / 481 / 781 ms, e os klines (que nascem no chunk 1)
custam 7 ms.

**A correção, sem índice novo.** A PK `(series_key_id, symbol, source, bucket_end, observed_at)` já ordena o
`bucket_end` **dentro** de `(série, símbolo, source)`. `DISTINCT ON (source) … ORDER BY source, bucket_end` vira um
`Custom Scan (SkipScan)` por chunk: **0,9 ms, 0 heap fetches**.

```sql
SELECT (SELECT min(b) FROM (SELECT DISTINCT ON (source) bucket_end AS b FROM md.series
          WHERE series_key_id=%s AND symbol=%s ORDER BY source, bucket_end) x),
       (SELECT max(bucket_end) FROM md.series WHERE series_key_id=%s AND symbol=%s)
```

| | antes | depois |
|---|---|---|
| liquidação (`MIN`) | 1.107–1.665 ms | 4–5 ms |
| klines (`MIN`) | 7 ms | 32–48 ms |
| `MAX` | 4 ms | 4 ms (fica no plano atual) |
| resultado, 10 séries de BTCUSDT | — | **10/10 iguais** `[MEDIDO]` |

- **O `MAX` NÃO vira `DISTINCT ON … DESC`:** essa forma não usa SkipScan e mediu 850–1.060 ms `[MEDIDO]`.
- **Risco declarado:** o `MAX` atual degrada, de forma espelhada, para uma série **morta**, isto é, uma que parou de
  gravar há muitos chunks. Hoje nenhuma das 10 está nesse caso.
- **Recusado: índice novo `(series_key_id, symbol, bucket_end)`.** A PK custa **2.195 MB** e o heap 2.727 MB
  `[MEDIDO: pg_relation_size por chunk]`. Um índice de 3 colunas custaria a mesma ordem de grandeza, no disco que já
  está sob pressão.

### 1.3 Por que 10 pedidos em paralelo dão a soma

- `get_series_history` é `def` síncrono e roda no threadpool do anyio.
- O `window_reader` é **uma** `psycopg.Connection`, montada uma vez em `src/main/__init__.py:260`, e a conexão
  serializa as consultas.
- A parte de CPU (o parse de linhas e o `as_of_batch`) segura o GIL.

Medido assim: em paralelo, 6,06–7,27 s de parede para uma soma sequencial de 7,09 s, e a CPU da API ficou em
2,7–3,5 s dentro dessa parede (`/proc/1/stat`). **Thread a mais não ajuda. Só processo a mais ajuda.**

### 1.4 As 10 em paralelo: cliente, servidor ou rota agregada

- **Cliente: já é paralelo** (`Promise.all`). Uma carga de página faz **11** chamadas, o catálogo (6–12 ms) mais as
  10 séries `[MEDIDO: docker logs --since]`. Nada muda em `web`.
- **Servidor: sim, por workers (§2).**
- **Rota agregada: recusada.** Ela poria as 10 séries em **um** worker, a soma de novo, e quebraria o endereçamento
  por conteúdo de `ADR-005/D1` (1 série = 1 URL cacheável). É mudança de contrato para comprar zero.
- **A página SSR inteira** mede 11,1–14,5 s (n=8, HTML de **11,1 MB**, TTFB ≈ total) sob a carga das 16h30. Na mesma
  janela, a tela só de API mediu 11,4–12,3 s, e a CPU do `next-server` foi 2,1–2,6 s por página (n=3). **A API é
  quase toda a página.** O resto (montagem de painéis e 11 MB de RSC) é do `frontend-architect`.

### 3.2 Por que excluir uma observação repetida não muda o `as_of` (a prova e o que a sustenta)

O `as_of` é `argmin(observed_at)` sobre as linhas admitidas. Uma linha é admitida quando
`available_at ≤ K ∧ observed_at ≤ K ∧ bucket_end ≤ t ∧ is_final is not False` (`domain/as_of_accessor.py`).

Seja `e` uma linha já gravada e `r` uma nova com o **mesmo fato**. Se `e.observed_at < r.observed_at` e
`e.available_at ≤ r.available_at`, então, para qualquer `(t, K)`:

- se `r` é admitida, `e` também é;
- e `e` ganha o `argmin`.

⇒ `r` **nunca** é a resposta, e não gravá-la não muda nenhuma resposta para nenhum `K`.

**A premissa foi medida:** dentro de um bucket, o `available_at` nunca desce quando o `observed_at` sobe. São **0
violações** em 614.990 linhas de BTCUSDT nos últimos 14 dias, nas 6 `source` `[MEDIDO: lag(available_at) over
(partition by série, bucket order by observed_at)]`. O `openInterestHist` é `MODELED`, com `available_at −
observed_at` de até **−7 dias**, e mesmo assim é monotônico.

**A prova também foi feita na prática, do lado da leitura:** uma sonda que entrega ao `as_of` só a primeira linha de
cada fato (`DISTINCT ON (source, bucket_end, is_final, value_raw, provenance, availability_source) ORDER BY …,
observed_at, available_at`) devolveu envelopes **idênticos** em **60/60** comparações. São 10 séries × 1m/1h/4h × a
janela de agora e uma 14 dias atrás (a região densa), mesmo `K`, com o sha256 do JSON sem `server_now_ms`
`[MEDIDO: cmp.py]`.

### 3.3 Onde: no escritor único, em um ponto só

**Decisão:** em `use_cases/write_series_row.py`, antes de `sink.accept`, entra um segundo predicado de leitura,
`identical_fact_present(row)`. Quando ele é verdadeiro, o desfecho é **`SKIPPED_IDENTICAL_FACT`**, que é terminal e
durável como os outros (o item do stream recebe `ack`).

**O fato** é `(series_key_id, symbol, source, bucket_end, event_time, is_final, value_raw, provenance,
availability_source, principal_id)`. A linha existente tem de ter `observed_at < r.observed_at` e
`available_at ≤ r.available_at`. Com isso as duas premissas do §3.2 viram **parte do predicado**, e não uma
suposição.

| | |
|---|---|
| **custo** | 0,12 ms por linha no servidor, pela PK, com exclusão de chunk em runtime (15 de 16 excluídos) `[MEDIDO: EXPLAIN ANALYZE em 3.000 linhas amostradas de 3 dias, BTC+ETH; 1.850/3.000 = 62% eram repetição]`. O escritor processa ~175 linhas/s (~5,7 ms/linha, `T-05.3`), então o acréscimo é ~2–5% `[INFERRED]` |
