# T-05.3 — build: buracos de klines que o boot não fecha

Componente `sentimento` · plano `docs/plans/SPEC-009-paineis-de-fluxo/05_correcoes_de_uso.md` item 5.3 / DoD 3 ·
defeito `D-C` de `handoff/FIX-uso-2026-10-02.md`.

## 1. Causa — `[MEDIDO 2026-10-02]`

**O backfill de boot do coletor publicava no aparador do stream.** `XADD ... MAXLEN ~ 100000` descarta as
entradas mais antigas passado o teto **lidas ou não pelo escritor**, sem erro. O boot publica
`7 x 1440 x 4 símbolos x 6 identidades = 241.920` entradas em ~26 s; o escritor drena ~175 linhas/s.
`klines_backfill_cli` (o one-shot de 90 dias) já esperava o lag do grupo (`XINFO GROUPS`); o boot do
coletor (`collectors_cli._collect_klines_for_symbol`) não. O comentário de `deploy/compose.yml` que
dimensionava o pico ainda contava **uma** linha por barra ("40.320, 40% do teto") — deixou de valer
quando a barra virou seis linhas (`T-01.3`/`SPEC-008`).

Evidência (todas leitura; `Q` = `docker exec -i deploy-postgres-1 sh -c 'psql -U $POSTGRES_USER -d $POSTGRES_DB'`):

| fato | comando | resultado |

| o escritor recebeu ~43% | `docker logs -t --since 2026-10-01T20:11:00Z --until 2026-10-01T20:21:30Z deploy-writer-1 \| grep -o 'n_accepted=[0-9]*'` somado | `105.334` linhas em 1.059 lotes, contra `40.317 x 6 = 241.902` publicadas |

**E por que o poll contínuo também não fecha:** o ciclo pede só as `tail_limit = 3` barras mais novas
(`_tail_limit`, `collectors_cli.py`), qualquer que seja o watermark. Minuto que ficou para trás de 3 barras
nunca mais é pedido dentro do processo. Com o freio novo o boot passa a durar minutos — sem tratar isso,
o fix CRIARIA buraco no primeiro símbolo.

## 2. Correção na origem

- `backend/src/modules/sentimento/infra/redis_stream_backpressure.py` (novo): `read_group_lag` e
  `StreamGroupMissingError` saíram de `klines_backfill_cli` (o coletor não podia importá-los de volta —
  ciclo de import); `lag_ceiling_for(maxlen) = maxlen // 5` (20.000 no default, o número do one-shot);
  `StreamDrainGate` — espera sem timeout até `lag <= teto` ou `SIGTERM`, conexão **própria e preguiçosa**
  (a conexão do sink é compartilhada por 7 threads sem lock; um `XINFO` nela poderia ter a resposta lida
  por um `XADD`), grupo inexistente = espera, não crash.
- `collectors_cli.py`: toda página **andada** espera o gate antes de publicar; o ciclo que está atrás do
  watermark (`_catch_up_cursor`) anda a partir de `watermark + 1 barra` em vez de pedir o tail;
  `BootConfig.redis_stream_group` (`REDIS_STREAM_GROUP`, default `single_writer`);
  `default_klines_drain_gate(config)` é o que `run()` usa.
- `klines_backfill_cli.py`: importa o probe do módulo novo e o grupo de `boot.redis_stream_group`.
- `deploy/compose.yml`: comentário do pico corrigido (241.920, não 40.320), com a correção datada.

## 7. Fora de escopo, nomeado

- **Gatilho dos restarts:** falha de DNS no `client.klines` é classificada como falha de publicação
  (`OSError` em `_PUBLISH_FAILURE_EXCEPTIONS`) e derruba o processo inteiro. Com o fix o restart deixa de
  abrir buraco, mas continua custando um re-walk de 7 dias. Candidato a task própria.
- **Conexão Redis compartilhada sem lock** entre as 7 threads do coletor (`RespConnection` não tem lock):
  entre dois `XADD` a troca de resposta é invisível; o gate novo foi isolado dela, o resto não.
- O boot do `openInterestHist` (8.064 pontos) não passa pelo gate; cabe folgado sob o teto com o klines
  freado (20.000 + 9.000 + 8.064 < 100.000).
