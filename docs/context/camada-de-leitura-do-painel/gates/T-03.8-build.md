## 1. O que foi feito

1. **`frontend/src/features/s1-console/view-model.ts`** — as três funções hand-rolled
   (`formatPtBrThousands`, `formatPtBrDecimal` — vírgula — e `formatDotDecimal` — ponto, usada
   deliberadamente para uptime%/GB-dia para reproduzir a tela canônica aprovada) foram
   substituídas por **uma única** `formatPtBrNumber(value, fractionDigits)`, construída sobre
   `new Intl.NumberFormat("pt-BR", { minimumFractionDigits, maximumFractionDigits })`. A
   docstring anterior do módulo argumentava que `toLocaleString`/`Intl` deveriam ser evitados por
   lerem "o locale de runtime" — verdade para uma chamada SEM locale explícito
   (`value.toLocaleString()`, `Intl.NumberFormat()` sem argumento), que resolve contra o locale
   PADRÃO do host; **não vale** para `new Intl.NumberFormat("pt-BR", …)`, cujo argumento
   explícito fixa a saída independente de onde o código roda — mesmo determinismo das funções
   manuais, só que sobre o formatador da própria plataforma. Docstring corrigida para essa
   distinção, citando `T-03.8`/`SPEC-003` §3.7 como a decisão que fecha o split de marca decimal
   que a revisão anterior registrava como "fora de escopo" (`D7.12`-`D7.15`).
   Todos os call-sites (`retentionCellText`, `resilienceCellText`, `statusCellText`,
   `buildStorageBudgetView`) migrados para `formatPtBrNumber`. Efeito colateral MEDIDO e
   documentado: uptime%/GB-dia/multiplicador SLO passam de ponto para vírgula decimal
   (`"99.8%"` → `"99,8%"`, `"1.6 GB"` → `"1,6 GB"`, `"~4.7x"` → `"~4,7x"`) — os agrupamentos de
   milhar (`"2.206"`, `"14.204"`) não mudam, porque pt-BR usa `.` para milhar nos dois casos.
2. **`frontend/src/features/s1-console/view-model.test.ts`** — 2 testes de formatador renomeados
   (`formatPtBrThousands`/`formatPtBrDecimal` → `formatPtBrNumber`, mesmos vetores), 1 teste novo
   provando que o MESMO formatador cobre uptime%/GB-dia (99,8 / 4,7 / 1,2 — nunca mais dois
   formatadores concorrentes); 2 asserções de texto atualizadas para a vírgula
   (`resilienceCellText` "T1m / SLO ~4,7x"; `buildS1ViewModel` orçamento total "1,6 GB"). As
   asserções de milhar (`"2.206"`, `"14.204"`) e as de dias com vírgula que já existiam
   (retenção, "1,5 dia"/"7,0 dias") **não mudaram** — já batiam com o formatador único.
3. **`frontend/e2e/07-locale.spec.ts`** — reescrito por inteiro (3 testes, não 1):
   - **`D3.5`** (rótulo ≠ coluna): `<th>` contém "Janela de perda" (1 ocorrência), nunca
     "JANELA_DE_PERDA" (0 ocorrências) — medido contra a página ambiente real de `make e2e`.
   - **`D3.4`** (uma marca decimal só): a suíte anterior era `expect.soft` sobre a página
     AMBIENTE, que — medido ao vivo, ver §2 — nunca alcança um decimal real (`retention`/
     `resilience` gated a `unmeasured`/`not_scored` pelo fio de `ADR-030`; só `uptimePercent`
     pode carregar fração). Reescrito como teste HARD, com um stub HTTP próprio (mesma técnica de
     `startSecondaryNextInstance`/`02-rede-e-estados.spec.ts`) devolvendo `uptimePercent: 99.8` —
     prova que o decimal REALMENTE chega à tela como `"99,8%"` (`commaDecimal.length > 0`) e que
     **nenhum** ponto decimal sobrevive ao lado dele (`dotDecimal === []`).
   - **ambiente**: mantido como registro de fatos (soft), não gate — a página seedada por
     `make e2e` hoje não produz decimal algum (declarado, não escondido).
4. **`frontend/e2e/01-painel-carrega.spec.ts`** — o grep de vazamento de fixture (`B7`) usava o
   literal `/1\.6 GB|99\.8%/` (formato ANTIGO, ponto decimal); com o formatador único agora em
   vírgula, esse padrão nunca mais casaria mesmo que a fixture vazasse — falsificador морto por
   `rc=0` silencioso. Atualizado para `/1,6 GB|99,8%/`, mesma finalidade.

## 2. Achado medido, não hipótese — por que a métrica antiga era vazia

Antes de reescrever, medi a página ambiente (backend real, seed padrão de `make e2e`, 1 run):

```
curl -s $API/api/v1/collector-status
  -> {"rows":[{"uptimePercent":null,"retention":{"kind":"unmeasured"},
              "resilience":{"kind":"not_scored"}, ...}]}
```

`comma_decimal_hits=[]` e `dot_decimal_hits=[]` — **os dois zero**, não porque o formatador
unificou nada, mas porque nenhum número com fração chega à tela nesse estado (retenção/orçamento/
reconexões são todos `SourceNoneMarker` em `F1`, `budgetSourced`/`reconnectionsSourced` hard-
`false`). A verificação `comma_decimal_hits = 0 OU dot_decimal_hits = 0` (D3.4 do plano) passaria
mesmo SEM a mudança de código, de forma vácua — por isso o teste novo usa um stub HTTP com
`uptimePercent: 99.8` para provar o caso NÃO-trivial (decimal real, vírgula, sem ponto ao lado).
