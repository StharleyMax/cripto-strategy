## O que esta rodada fez, e por que não repetiu a medição HTTP

A rodada anterior (commit `371d093`) já tinha medido, por HTTP direto (seed efêmero do store +
`uvicorn` + `next build`/`next start`, portas avulsas escolhidas na hora), todos os `DoD` de
comportamento: `ui_state:ok/empty/error` (3 causas distintas — `missing_base_url`,
`connection_refused`, `non_2xx`+`status`), access log incrementando só quando a API responde, 0
`<td>` em `empty`/no chão, 5 blocos `source:none`, `fixtures.ts` fora do grafo de produção, e nenhum
valor de `INGEST_HEALTH_API_BASE_URL` vazado no bundle. O único motivo do `NEEDS_FIX` foi doc delta
ausente — o commit não tinha `gates/T-01.4-build.md` nem linha em `docs/INDEX.md`, quebrando o padrão
de `T-01.1`/`T-01.2`/`T-01.3`/`T-01.10` na mesma feature.

Esta rodada:
1. Recriou a branch a partir de `origin/master` atualizado (`git rebase origin/master`, sem
   conflito) — o rebase só reposiciona o commit; `git diff 371d093 HEAD` sobre os 8 arquivos de
   produção é **0 linhas**, confirmando que o código medido pela rodada anterior é byte-a-byte o
   mesmo que chega nesta.
2. Re-executou lint, typecheck e as 4 suítes `node --test` do front sobre o código pós-rebase, para
   confirmar que nada quebrou ao subir a base — todos batem com os números da rodada anterior
   (`test:s1` 60/60, `test:s3` 37/37, `test:app` 97/98 com a mesma falha pré-existente, `test:charts`
   141/157 com as mesmas 16 falhas pré-existentes).
3. Escreveu este arquivo e a linha de `docs/INDEX.md`, fechando o único item do `NEEDS_FIX`.

Não repetiu a medição HTTP porque ela já existe, é do mesmo código (diff vazio), e repeti-la sem
mudança de produção não altera o veredito — seria HTTP replay por HTTP replay do mesmo binário.
