## `CA-5b` — números medidos, e o mecanismo por trás deles

`range-dispatch.ts`'s `onPanelRangeChanged` converte o range do painel ORIGEM para TEMPO usando
o `axis` compartilhado, e converte de volta para um número lógico usando o MESMO `axis`,
escrevendo esse número **verbatim** em cada um dos outros painéis. Esse round-trip só é correto
**se e somente se** o mapeamento índice-lógico→instante de CADA painel for igual ao do `axis`
compartilhado (`D-C3.2`). O teste mede os dois lados dessa condição:

```
node --experimental-strip-types --test src/app/symbol/axis-sync-alignment.test.ts
# CA-5b CALA (6 painéis, 5.760 slots cada) ............ 0 min de desalinhamento
# CA-5b MORDE (6 painéis podados 5760/1152/5412/300/300/1152) .. desalinhamento MEDIDO = 5.423,6 min
```

`5.423,6 min` contra a referência histórica de `5.460 min` (`JULGAMENTO-FRONTEND-ARCHITECT.md:176`,
`loop-probe2.mjs`) — mesma ordem de grandeza, gesto e reconstrução diferentes (este teste faz UM
`setVisibleLogicalRange({from:1000,to:4000})` no painel de Preço; o probe original usava outro
gesto), o que é esperado: o ponto do `CA-5b` não é reproduzir o mesmo número ao dígito, é provar
que o instrumento MORDE (`>0`, e por uma ordem de grandeza consistente com o defeito histórico) e
CALA em exatamente `0` quando a invariante `D-C3.2` vale — os dois comandos, o mesmo arquivo.

O caso MORDE não é vácuo: se a medição de desalinhamento estivesse quebrada e sempre devolvesse
uma constante positiva, o caso CALA (que exige exatamente `0`, não "pequeno") teria reprovado.

## `DoD-2`/`DoD-3`/`DoD-4` — o que a instrumentação DOM prova, e o achado no meio do caminho

**Achado 1 — a direção do arrasto importa, e por quê.** Medido ao vivo:
`[MEDIDO 2026-09-21]` arrastar o mouse para a ESQUERDA nunca mudou `data-visible-logical-from`
em 10s de polling; para a DIREITA, mudou imediatamente (`-1 → -577`). Não é defeito desta task:
o `initialLogicalRange` cobre a grade canônica INTEIRA (4 dias), mas o dado real de BTCUSDT hoje
cobre bem menos candles reais que isso — o assentamento inicial (biblioteca clampando ao que
cabe em `minBarSpacing`) já pousa perto de uma borda real de dado, e arrastar NAQUELA direção não
tem para onde ir. `dragPricePanel` documenta isto e recusa `deltaXPx <= 0`.

**Achado 2 — um "gesto" não é UMA notificação, é um FLUXO.** A primeira versão do teste assumia
"1 gesto ⇒ +1 na contagem de escrita" e mediu `+47` num só arrasto contínuo: `lightweight-charts`
dispara `subscribeVisibleLogicalRangeChange` por QUADRO onde o range mudou, não uma vez por
gesto. Isso é comportamento correto (um arrasto real produz uma janela deslizante contínua), não
o laço de realimentação que `DoD-4` teme. O teste foi refeito para medir a propriedade que
`DoD-4` de fato pede: **lockstep** (os 5 painéis recebem o MESMO número de escritas a cada
rodada — `new Set(deltas).size === 1`, morde numa amplificação assimétrica) e **ausência de
laço** (depois do último gesto assentado, esperar 1s sem nenhum input novo não pode mover os
contadores — morde numa realimentação contínua).

Números medidos, uma corrida completa (`make e2e`):

```

gesto 0 (Δ=150px): from=-283 (idêntico nos 6)   delta=+47 nos 5, +0 no Preço
gesto 1 (Δ=260px): from=-783 (idêntico nos 6)   delta=+48 nos 5, +0 no Preço
gesto 2 (Δ=90px):  from=-949 (idêntico nos 6)   delta=+46 nos 5, +0 no Preço
após 1s sem gesto: contagens IDÊNTICAS às do gesto 2 (145/145/147/147/147) — sem laço
```

`DoD-3`/ablação (`?e2eAxisSyncDisabled=1`), mesma página, mesmo gesto (`Δ=150px`):

```
Preço: from -1 → -283 (o arrasto NATIVO continua funcionando — só o despacho foi desligado)
oi/cvd/liq_long/liq_short/long_short: from -1 → -1 (NENHUMA mudança), write_count = 0 nos 5
```
