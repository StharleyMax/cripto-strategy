efeito que um módulo puro, sem `jsdom` e sem a biblioteca (`D-C3.1`), não tem como reproduzir
nem tem razão para fingir que reproduz. O que este teste prova é a parte que É deste módulo: a
aritmética de conversão em si não introduz NENHUM erro (round-trip exato, já provado por
`T-02.2`); o resíduo de `2,7 h` nasce depois, na fronteira com a biblioteca real (`T-02.4`).

## Achado de processo, registrado porque custou um ciclo de correção

Ao rodar `npm --prefix frontend run test:charts` com um `--test-name-pattern` recortado (para
economizar saída), `eslint-boundary.test.ts` **reprovou 5 testes** que nada tinham a ver com
este diff (`ADR-034/D8`, `D5.12`). Reproduzido também com a suíte inteira. **Causa raiz:**
`eslint` real, rodando sobre a árvore inteira via `spawnSync`, encontrou os 2 erros
`prefer-const` nos dois arquivos novos de teste — o que faz o eslint devolver `rc≠0` também
para os arquivos **ephemeral** que o próprio teste planta/remove, quebrando a asserção "código
real fica limpo depois de remover os violadores". **Confirmado por diferença:** `git stash`
com os 4 arquivos novos fora → suíte 214/214 verde; com eles dentro e o `prefer-const`
corrigido → 228/228 verde. Ou seja: **um lint error em qualquer arquivo do `charts` pode
derrubar o `eslint-boundary.test.ts` inteiro**, não só o `lint` — vale para quem depurar um
`eslint-boundary` vermelho no futuro sem tocar o próprio arquivo do boundary.
