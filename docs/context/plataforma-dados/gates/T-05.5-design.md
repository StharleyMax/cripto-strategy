### Achado 2 — a série exibida no painel de Preço é, de fato, `klines_last` (preço negociado), não a marca

`S2_PRICE_USE = "structure_detection"` (`s2-panels.ts`) resolve para `klines_last`, e os candles vêm de
`data/binance/klines/tf2/BTCUSDT-1m-*.csv` (`s2-klines-loader.ts`) — dump de klines Binance real
(open/high/low/close/volume do trade, não `markPriceKlines`). Isso é a escolha correta para
`structure_detection`: swing/BOS/CHoCH precisam do preço negociado, não da marca 1 Hz subamostrada —
exatamente o motivo que `price_source_catalog.py:168-170` documenta para `klines_last`. **Não há troca
de grandeza**: o painel de Preço não está, por engano, mostrando `mark_price` rotulado como preço de
estrutura.

## O que fica em aberto — declarado, não escondido

**Risco de drift entre a tabela Python (`ADR-007` canônica) e a transcrição TS**, não coberto por
nenhum teste cruzado automatizado: `s2-price-source.ts` é uma "transcrição independente" deliberada
(sem import cross-language — a fronteira `charts`↔`web`/`backend` proíbe, `D5.12`), e isso está
declarado no próprio docstring do arquivo. Hoje as duas tabelas batem, 5/5 linhas, verificado linha a
linha acima. Mas se `ADR-007` for emendada no futuro e só o lado Python for atualizado, nada aponta de
volta para `s2-price-source.ts` — `price_source_catalog.py` não tem comentário recíproco citando o
arquivo TS. **Não é defeito desta task** (a decisão de não importar cross-language é arquiteturalmente
correta), mas é uma lacuna de governança que vale registrar como ação de backlog, não como condição
bloqueante — a tabela tem 5 linhas e baixa taxa de mudança histórica.
