## O que este gate NÃO pôde auditar, e por quê — registrado, não escondido

**O módulo de transporte SSE em si ainda não existe** — `find frontend/src -iname '*sse*' -o -iname
'*live*' -o -iname '*envelope*'` (2026-09-02) não lista nenhum arquivo; `tasks.toml:1100` marca
`T-08.11` como `status = "todo"`, `depends_on = ["T-05.9"]` (já `done`). Mesma postura de `T-05.9`: este
gate fecha a pergunta de **arquitetura de tela** (não há nenhuma nova) e **não** substitui o `ux-audit`
de nomenclatura que roda **depois** do `/build`, sobre o código real — nomes de campo do envelope
(`bucket_open_ts`, `cvd_delta_parcial`, `n_trades`, `seq`) só podem ser auditados contra convenção de UI
quando existir consumidor real renderizando algo com eles (`T-08.12`, painel).

**Recomendação registrada para quem construir, não uma decisão travada:** o campo de tempo do envelope
deveria manter a mesma convenção de nome que `T-05.8` fixou (`knowledge_time`/`asOf`) onde aplicável —
`bucket_open_ts` é campo de payload do ADR, não nome de parâmetro de URL, então não há conflito direto
hoje. `[NÃO SEI]` se o builder introduzirá algum parâmetro de URL ou estado de UI novo ao consumir o
stream (ex.: indicador de reconexão); falsificador: se aparecer um elemento visual novo de progresso ou
erro de conexão SSE que não está descrito na `S2` atual, este veredito fica obsoleto e a task precisa
voltar a este agente antes de qualquer merge.
