## O que este audit NÃO consegue julgar — `[NAO SEI]`, declarado

Não há leitura estática que alcance estes pontos porque nenhum código de render existe nesta branch:

- **`[NAO SEI]`** como o selo realmente aparece ancorado sob o crosshair (posição, sobreposição entre painéis, o que acontece quando 6 badges competem por espaço vertical).
- **`[NAO SEI]`** tamanho de alvo de toque/clique — não há CSS nem elemento no DOM para medir.
- **`[NAO SEI]`** contraste de cor da "tinta fraca" (`MODELED`) vs "tinta normal" (`OBSERVED`) — nenhum token de cor é declarado neste módulo; isso é item `5.9`/`T-05.7`, tarefa separada. `node scripts/validate_palette.js` não tem o que medir aqui (zero cor introduzida por este diff).
- **`[NAO SEI]`** timing/motion — nenhuma animação, transição ou `requestAnimationFrame` no diff.
- **`[NAO SEI]`** se a mensagem técnica de `NegativeAgeError` (guard de dado, não erro de usuário) algum dia vaza para uma superfície end-user — hoje é `throw` de módulo puro, sem caminho até UI.

## Pontos fortes

1. **A ausência de decisão de render não esconde decisão de UX já tomada errada** — ao contrário, as decisões de conteúdo que ESTE módulo toma (4 estados de idade, glifo `~` redundante à cor, formato fixo do selo, `completude` por `gapRuns` contíguos em vez de subtração ingênua) são todas **compatíveis e favoráveis** ao requisito de acessibilidade do item 5.3, não hostis a ele.
2. **Escopo declarado, não escondido** — o gate doc do builder nomeia explicitamente o que fica de fora (render/DOM, `D5.1`/`D5.2`/`D5.4`) em vez de deixar a lacuna implícita. Isso é exatamente a disciplina que evita o modo de falha que este mesmo repositório já documentou (decisão de design tratada como fechada sem estar).
3. **`~` como sinal não-cor** para `MODELED` é a escolha certa arquiteturalmente — remove, de saída, o risco clássico de "só cor" que normalmente só é pego tarde, na revisão de CSS.

## Condições (não bloqueiam esta task — bloqueiam a task que MONTA o selo em DOM real)

1. **Campo `idade` vazio precisa de representação explícita no render**, não string vazia solta no layout — placeholder neutro (ex.: célula omitida do grid do selo com regra de layout documentada, ou traço "—" com `aria-label` que declare "fora da janela visível") para que `absent` não seja lido como selo quebrado.
2. **Preservar o glifo `~` (ou equivalente textual/`aria-label`) no render final**, mesmo depois que a "tinta fraca" (cor) for adicionada por `T-05.7` — a cor nunca pode ser o único canal que distingue `OBSERVED` de `MODELED` (WCAG 1.4.1). Se o CSS de `T-05.7` chegar antes e algum PR remover o `~` "porque a cor já mostra", isso é regressão de acessibilidade e deve reprovar naquele gate.
3. **Layout do selo (6 painéis × 4 campos sempre visíveis) precisa de hierarquia tipográfica/agrupamento deliberado** na task de render — não é aceitável simplesmente empilhar 24 rótulos de texto no mesmo peso visual. Isto não é uma reprovação da `SPEC` (o requisito "sempre visível" é do produto, não deste builder), é uma condição de COMO satisfazer esse requisito sem violar H8.
4. Quando o `aria`/DOM real existir, rodar accessibility-check (`ux-ui-mastery:accessibility-check`) contra o componente montado — este audit não substitui aquele, só impede que decisões de conteúdo já erradas cheguem até lá.

## O que este audit NÃO julga

Fidelidade do dado (`quant-architect`): se `idade = tempo_de_referência − available_at` está semanticamente certo, se `provenance` está correto por painel, se o içamento em 3 níveis (`SessionEnvelope`/`PanelEnvelope`/`CellEnvelope`, item 5.4) representa o modelo de custo certo do `ADR-005`/D3 — nada disso é escopo deste gate. Note-se que o item 5.4 (içamento) é, na sua essência, uma decisão de **custo de payload/arquitetura de dados**, não de interação — este audit não a tratou como superfície de UX porque não é uma.

## Veredito: **APROVADO COM CONDIÇÃO**

Nenhum achado bloqueia o merge deste módulo — é lógica pura, sem tela, sem antipadrão de interação introduzido, e as decisões de conteúdo embutidas favorecem acessibilidade em vez de a colocarem em risco. As condições acima **vinculam a próxima task que monta o selo em DOM real** (a que o builder já nomeou como pendente), não esta.
