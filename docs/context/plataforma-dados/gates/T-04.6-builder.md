## O que já existia (medido antes de escrever qualquer linha)

Um teste de `T-02.3` (`test_ingest_record_durability.py::
test_the_cli_projection_is_byte_identical_under_pt_br_and_c_locales`) já roda exatamente esse
protocolo sobre a projeção do `ingest_health_cli`. O comentário em `series_key.py` já nomeava
esta task como dona de uma dívida específica: duas cópias byte-idênticas do serializador JSON
canônico (`_canonical_json`), uma em `series_key.py` e outra em `ingest_record.py`. E a própria
docstring do teste de `T-02.3` confessava uma lacuna: toda coluna da projeção hoje é `int`,
`str` ou `null` — nenhum `float` foi testado sob os dois locales.

Levantamento completo do componente (`grep -rn "locale\|LC_ALL\|LC_NUMERIC\|format_string"
backend/src/modules/sentimento backend/tests/sentimento backend/tests/helpers`, n=0 uso real de
API sensível a `LC_NUMERIC` fora do teste de `T-02.3`) confirmou: nenhum outro caminho usa
formatação dependente de locale hoje — `json.dumps` (usado em todos os pontos que serializam
`float`/`int`) é invariante por construção (`float.__repr__` sempre usa ponto). O único
`float` de produção que nunca foi testado sob os dois locales é o payload de
`infra/quota_ramp_cli.py::emit()` (`recoil_seconds`, `weight_per_blind_request`, …).

## Falsificador — o teste novo REJEITA um defeito real, não passa por vácuo

Mutante temporário (nunca commitado, restaurado byte a byte depois): o driver trocou o `float`
`1234567.891011` do payload por `locale.format_string("%f", …, grouping=True)`.

```
$ .venv/bin/python -m pytest tests/sentimento/test_quota_ramp_locale_invariance.py --no-cov -v
FAILED […][pt_BR.UTF-8] — AssertionError: hash 0986dc15… != 26d06009…
PASSED […][C]
```

Sob `pt_BR.UTF-8` a diferença aparece (`sha256` diverge); sob `C` os dois formatos coincidem
(esperado, já que `C` não separa milhar nem troca a vírgula). Restaurado, suíte volta a verde
(`2 passed in 0.36s`).
