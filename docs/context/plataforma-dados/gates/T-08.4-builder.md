## O que foi construído

`backend/src/modules/backtest/` nasce nesta task (segundo contexto de código Python do
vocabulário, depois de `sentimento`):

- **`domain/intrabar_convention.py`** — `IntrabarConvention(StrEnum)`, hoje um membro
  (`PESSIMISTIC_STOP_FIRST`), espelhando o `CHECK` da coluna.
- **`domain/run_registry_entry.py`** — `RunRegistryEntry` (dataclass frozen, as 10 colunas de
  `ADR-021`/D2, sem `created_at`, que é `TIMESTAMPTZ DEFAULT now()` do lado do banco e nunca
  passa por `domain`/`use_cases`). `__post_init__` recusa: identificador vazio, hash que não é
  64-hex-minúsculo, janela invertida, `knowledge_time` negativo, `intrabar_decided_count`
  negativo. `intrabar_convention`/`intrabar_decided_count` são campos obrigatórios sem default
  — G4 é garantido por TIPO (Python recusa a chamada antes de `__post_init__` rodar), não por
  branch de validação.
- **`domain/bundle_hash.py`** — `bundle_hash(bundle) = sha256(canonical_json(_canonicalize_dict(bundle))).hexdigest()`,
  reusando `src.modules.sentimento.domain.canonical_json` (direção permitida pelo
  `import-linter`, `ADR-021`/D3). **Corrigido em 2026-09-04, ciclo de QA `NEEDS_FIX`:** a
  primeira versão chamava `canonical_json(bundle)` direto — `sort_keys=False` por design (os
  outros call-sites de `sentimento` dependem de ordem de inserção como contrato de coluna) —
  o que tornava o hash sensível à ordem de campo do dict de origem, o cenário que a própria
  `ADR-021`/G3 nomeia como falsificador de `D3`. QA provou com teste vermelho
  (`test_bundle_hash_determinism_qa.py`); a correção adiciona `_canonicalize_dict`, que
  reordena chaves recursivamente (equivalente schema-free ao `PARAM_ORDER` fixo de
  `threshold-spec-bundle.ts:369`) antes de `canonical_json` — ordem de LISTA é preservada
  (é dado, não campo). Ver `docs/adr/ADR-021-...md`, "Emenda 2026-09-04".
- **`domain/knowledge_time.py`** — `resolve_knowledge_time`, os dois modos de `ADR-021`/D4
  (`LIVE`: `max(observed_at)` pós-run; `PINNED`: confere `achieved <= pinned`).
- **`use_cases/record_run.py`** — `record_run()` + `RunRegistryStore` (`Protocol`) +
  `RunRegistryDivergenceError`. Implementa G1 (mesma tripla, hash diferente ⇒ recusa citando
  os dois `run_id`/hashes) sem reabrir G2: `partitions_content_hash` é **opaco** aqui (mesma
  filosofia de `bundle_hash` em `ADR-021`/D3) — este `use_case` nunca recusa só porque a tripla
  se repete, e distinguir compactação de dado novo continua sendo `ADR-002`/D6 (`sentimento`,
  item 8.2), rio acima desta chamada. Decisão de builder, registrada aqui por não estar em
  nenhuma ADR: **nenhuma tabela nova de `partition_touch` foi criada** — considerei e descartei
  essa rota (ela exigiria comparar listas de partição por partição, que é exatamente o
  mecanismo que `ADR-002`/D6 já possui do lado de `sentimento`; duplicá-lo aqui seria a mesma
  classe de defeito que `ADR-021`/D3 nomeia para um segundo serializador).
- **`infra/postgres_run_registry_store.py`** — `PostgresRunRegistryStore` (psycopg real,
  conexão injetada), `SCHEMA_SQL` (DDL 1:1 com `ADR-021`/D2), `ensure_schema`/`find_by_triple`/
  `find_by_run_id`/`record`, mais o mapeador puro `_row_to_entry`/`_row_created_at_ms`.

**Fora do escopo desta task, nomeado:** o motor/engine de backtest não existe — `record_run`
está pronto para ser chamado por ele, mas nada aqui orquestra uma simulação. `D8.9` completo
(critério da fase 08) só fecha quando esse motor existir e chamar este código; o que esta task
fecha é a garantia AO NÍVEL DE `run_registry`, testada com triplas fabricadas.
