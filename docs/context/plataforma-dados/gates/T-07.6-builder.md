## 1. Ciclo de correção — o handoff chegou DEPOIS da primeira implementação

A worktree foi criada de `master@bf15df6`, e nesse commit
`docs/context/plataforma-dados/handoff/T-07.6.md` **não existia** (verificado por `ls` no
diretório de handoff, ausente entre `T-07.5.md` e `T-07.7.md`). Reconstruí o escopo de fontes
primárias (`tasks.toml`, o plano, `PRD-001`, `docs/recorte-plataforma.md`) e implementei uma
primeira versão que reservava, por partição, o pico medido (`max`) para exatamente UM símbolo e
a carga estável (`p50`) para cada outro — uma leitura conservadora, mas mais fraca que a exigida.

Antes do commit, `git fetch origin` (disciplina do próprio protocolo de despacho) achou
`origin/master@b550a47`, com o handoff mesclado em paralelo. O handoff é literal sobre a fórmula:
*"use o máx 3.224 msg/s como orçamento por partição, não o p50 — dimensionar pelo p50
sub-provisiona e derruba consumidor no pico real"*, e nomeia o falsificador esperado: um cenário
onde N símbolos podem atingir o máx **simultaneamente** tem que caber na capacidade.

Corrigi a fórmula de dimensionamento (`n * max <= capacity`, não a reserva assimétrica) e
acrescentei `partition_count` + o teste de falsificação nomeado, **antes de qualquer commit
desta task** — nenhum código com a fórmula antiga foi publicado.

## 3. O que foi implementado

`domain/stream_partitioning.py`:
- `SingleSymbolThroughput` — dataclass congelado com os 5 percentis; `__post_init__` recusa
  valores negativos ou não-monotônicos.
- `MEASURED_SINGLE_SYMBOL_THROUGHPUT` = `D7.11` verbatim (p50=21, p95=204, p99=483, p999=1251,
  max=3224).
- `max_symbols_per_partition(capacity, throughput)` = `capacity // throughput.max` — todo
  símbolo da partição orçado no seu pico medido, simultaneamente. Levanta
  `InfeasiblePartitionCapacityError` quando `capacity < max` (nem um símbolo cabe).
- `partition_count(symbol_count, capacity, throughput)` = `ceil(symbol_count /
  max_symbols_per_partition(...))`; `symbol_count <= 0` devolve 0 (universo vazio não é erro).
- `partition_symbols(symbols, n)` — chunking determinístico, ordem preservada (identidade de
  reconexão de um coletor WS, `ADR-004`).

`infra/stream_partition_plan.py`: `plan_stream_connections(symbols, capacity, stream, throughput)`
compõe `max_symbols_per_partition` + `partition_symbols` com `combined_stream_path` (`T-03.1`,
`infra/binance_stream_probe.py`) para devolver a tupla de paths WS já particionados — reusa a
infra existente (chamada hoje só pelo probe CLI) em vez de reimplementá-la.

**Somente `max` alimenta a aritmética.** `p50`/`p95`/`p99`/`p999` viajam no dataclass para que a
régua inteira não divirja de `D7.11` sem que algo perceba, mas não entram no cálculo —
`test_only_max_feeds_the_sizing_arithmetic` prova isso comparando duas réguas que só concordam em
`max`.

## 4. DoD

- [x] **D7.11** — a vazão de um único símbolo é a entrada, verbatim, do dimensionamento:
  `test_measured_constant_is_d7_11_verbatim` compara `MEASURED_SINGLE_SYMBOL_THROUGHPUT` contra
  os 5 números literais do plano.
- [x] **Falsificador nomeado pelo handoff, literal**: "um cenário com N símbolos, cada um podendo
  atingir o máx medido simultaneamente, tem que caber dentro do número de partições que a função
  devolve — se o dimensionamento fosse feito pelo p50 ou p95, o teste tem que mostrar que o pico
  do pior caso estouraria a capacidade."
  `test_p50_based_sizing_would_overflow_capacity_under_simultaneous_peaks`
  (`test_stream_partitioning.py`) prova as DUAS metades na mesma asserção: a fórmula por `p50`
  rejeitada, aplicada à mesma capacidade (10.000 msg/s), produziria uma partição de 323 símbolos
  cujo pico simultâneo real (`323 × 3.224 = 1.041.352` msg/s) **excede a capacidade em 104×**; a
  fórmula por `max` implementada limita a mesma partição a 3 símbolos, cujo pico simultâneo
  (`3 × 3.224 = 9.672`) **cabe** dentro dos 10.000.
- [x] Capacidade abaixo do `max` medido é rejeitada, não silenciosamente aceita com 0 símbolos:
  `test_capacity_below_the_measured_max_is_infeasible`.
- [x] Composição ponta a ponta com a infra real: `test_stream_partition_plan.py` prova que
  `plan_stream_connections` produz o MESMO formato de path que `combined_stream_path` já produz
  para o probe.
