## Verificação dirigida (mentalidade destrutiva)

1. **`bundle_hash` determinístico sob reordenação de chaves — NÃO É.** `bundle_hash(bundle) =
   sha256(canonical_json(bundle))`, e `canonical_json` usa `sort_keys=False` (`insertion order
   IS the field order`, por design de `sentimento`). Testei eu mesmo:
   `bundle_hash({"universe":["BTCUSDT"],"window_days":30,"fee_bps":4})` ≠
   `bundle_hash({"fee_bps":4,"universe":["BTCUSDT"],"window_days":30})` — mesmo bundle lógico,
   hashes diferentes. **Isto é, literalmente, o critério que `ADR-021` define para si mesma
   como G3** ("dois valores de `bundle_hash` diferentes para o MESMO bundle, mesmos bytes
   lógicos, ordem de campo diferente" ⇒ derruba D3). O builder já tinha essa observação em mãos
   — `tests/backtest/test_bundle_hash.py::test_field_order_changes_the_hash` prova exatamente
   este caso — e a reclassificou em comentário como "não é defeito", sem nenhuma emenda de
   `ADR-021` registrando essa reinterpretação. O precedente que a própria `ADR-021`/D3 cita como
   modelo (`frontend/src/app/threshold-spec-bundle.ts:369` `bundleHash`) **não tem este
   problema**: ele hasheia `encodeBundle()`, que itera uma constante `PARAM_ORDER` fixa — a
   ordem nunca depende de como o chamador construiu o objeto. O lado Python, ao aceitar
   `dict[str, object]` cru sem esquema, não replica essa disciplina; deixa a ordem ao sabor de
   quem construiu o dict, o que é exatamente o cenário que dois pontos de chamada futuros
   (web vs reconstrução a partir de storage) podem divergir sem aviso. Escrevi
   `tests/backtest/test_bundle_hash_determinism_qa.py::
   test_g3_same_logical_bundle_different_field_order_must_hash_identically`, que roda **FALHA**
   — prova formal do defeito, não opinião.
2. **`knowledge_time` nunca lê relógio** — confirmado por leitura: `domain/knowledge_time.py`
   não importa `datetime`/`time`; `LIVE` é `max(observed_at_values)` (lista passada pelo
   chamador), `PINNED` confere `achieved <= pinned`. `grep` em `domain`+`use_cases` por
   `datetime`/`time` import: 0 ocorrências. `make natureza` confirma (0 leituras de relógio).
   O único relógio da tabela é `created_at` (`TIMESTAMPTZ DEFAULT now()`), auditoria, do lado
   do banco — consistente com `ADR-021`/D2/D4. **OK.**
3. **`intrabar_convention`/`intrabar_decided_count` genuinamente separados** —
   `RunRegistryEntry` exige os dois como campos obrigatórios sem default; `TypeError` na
   ausência de qualquer um dos dois (`test_omitting_intrabar_convention_cannot_construct_a_row_at_all`,
   reproduzido). Nenhum dos dois é derivado do outro em código (nenhuma função computa um a
   partir do outro). **OK, mas o cálculo real de `intrabar_decided_count` não existe ainda —
   correto, motor de estratégia é fora de escopo desta task, nomeado como tal.**
4. Reexecutei os 6 testes reais contra Postgres via docker (dentro dos 34 acima) — confirmados
   reais, não mockados (ver Baseline).
