# T-09.6 — auditoria do append-only de `docs/INDEX.md`

`CST-88`, componente `docs`. Esta task não escreve código nem acrescenta linha manual ao
`INDEX.md` — ela produz um falsificador reproduzível de que a disciplina append-only descrita em
`CLAUDE.md` §"Registro de artefatos é append-only" foi mantida desde a criação do arquivo
(2026-08-25, `/pm`, commit `9e23dbe`).

## O que "append-only" tem de garantir, e o que o falsificador mede

Toda linha já commitada de `docs/INDEX.md` tem de sobreviver, **byte a byte**, em todo commit
futuro — nova informação só entra como linha nova. Isso é equivalente a: em cada commit `C` com
pai(s) `P`, o conteúdo de `docs/INDEX.md` em `P` é uma **subsequência exata** (linha a linha,
igualdade de string, em qualquer posição) do conteúdo em `C`. Para commit de merge (2 pais), a
mesma checagem roda contra **os dois pais**, porque `CLAUDE.md` explicitamente permite resolução
de conflito de merge que **reordena** as entradas concorrentes por ordem cronológica sem
descartar nenhuma — o que quebra a ordem de uma checagem ingênua mas não quebra a garantia real.

## Falsificador (comando + universo)

Universo: **149 commits** que tocaram `docs/INDEX.md` desde a criação (`git log`, sem
`--follow` — o arquivo nunca foi renomeado, confirmado por
`git log --follow --name-status -- docs/INDEX.md` só mostrar status `A`/`M`, nunca `R`).
**`--follow` sozinho SUBCONTA este universo em 28 commits (121 vs 149)** — ele perde
sistematicamente os merges de 2 pais nesta árvore; por isso o comando abaixo usa `git log`
puro, não `--follow`.

```bash
git log --reverse --format='%H %P' -- docs/INDEX.md > /tmp/index_commits.txt
wc -l /tmp/index_commits.txt                      # 149
awk '{print NF}' /tmp/index_commits.txt | sort | uniq -c
#   1  1   <- commit raiz (sem pai, nada a comparar)
# 120  2   <- commit de pai único
#  28  3   <- merge de dois pais
```

```python
#!/usr/bin/env python3
"""Falsificador do append-only de docs/INDEX.md — subsequência exata linha a
linha do(s) pai(s) dentro do filho. Universo: os 149 commits de
/tmp/index_commits.txt (git log --reverse --format='%H %P' -- docs/INDEX.md)."""
import subprocess

REPO = "<raiz do repo>"

def get_lines(rev):
    out = subprocess.run(["git", "show", f"{rev}:docs/INDEX.md"],
                          cwd=REPO, capture_output=True, text=True)
    return out.stdout.splitlines() if out.returncode == 0 else None

def is_subsequence(small, big):
    it = iter(big)
    for line in small:
        if not any(b == line for b in it):
            return False
    return True
    # nota: a versão realmente usada devolve também o índice da falha,
    # omitido aqui por brevidade — ver corpo completo abaixo do resultado.

with open("/tmp/index_commits.txt") as f:
    rows = [l.split() for l in f if l.strip()]

violations = []
for commit, *parents in rows:
    if not parents:
        continue
    cur = get_lines(commit)
    for p in parents:
        base = get_lines(p)
        if base and not is_subsequence(base, cur):
            violations.append((commit, p))

print(f"UNIVERSO: {len(rows)} commits, {sum(1 for r in rows if len(r) == 3)} merges")
print(f"CANDIDATOS A VIOLAÇÃO: {len(violations)}")
for c, p in violations:
    print(f"  {c[:10]} (pai {p[:10]})")
```

## Triagem dos 8 candidatos — 3 são falso-positivo do instrumento (reordenação de merge, sem perda), 1 é auto-corrigido antes de chegar a `master`, e **4 são violação real**

A checagem por subsequência ORDENADA falsa-positiva exatamente onde `CLAUDE.md` prevê exceção:
merge que intercala cronologicamente as entradas dos dois lados. Refeita como checagem por
**multiset** (mesmas linhas, ignorando ordem) — `Counter(pai) - Counter(filho)` — para separar
"reordenado" de "perdido":

```bash
# exemplo do padrão rodado para cada um dos 3 merges flagados:
python3 -c "
from collections import Counter
import subprocess
def get(r): return subprocess.run(['git','show',f'{r}:docs/INDEX.md'],capture_output=True,text=True).stdout.splitlines()
print(Counter(get('<pai>')) - Counter(get('<filho>')))"
```

| commit | tipo | veredito |
|---|---|---|
| `add2c100ad` — *"merge: master (4 PRs) em T-03.1 — nenhuma linha do INDEX perdida, conferido por CONJUNTO"* | merge, 2 pais (`14ef986`, `9775c7e`) | **multiset OK, 0 linha perdida dos dois pais** — a subsequência ordenada falsa-positiva porque o merge intercala por timestamp; o próprio commit já se autodeclarava conferido por conjunto, e a conferência bate |
| `f7509288` — *"Merge remote-tracking branch 'origin/master'..."*, corpo: `# Conflicts:\n#\tdocs/INDEX.md` | merge, 2 pais (`5523167`, `1ad1434`), **conflito real e declarado** | **multiset OK, 0 linha perdida dos dois pais** — é exatamente o caso que `CLAUDE.md` nomeia: *"conflito de merge resolvido mantendo ambas as entradas concorrentes em ordem cronológica"* |
| `b235be5c86` — merge de `origin/master` para dentro de `tasks/T-07.4-fase07` | merge, 2 pais (`8de3832`, `34141bb0`) | pai 1 (`8de3832`) tinha a linha **corrompida** (ver abaixo); o merge adota a versão **correta** vinda do pai 2 — checado: as duas linhas certas (`T-03.6`, `T-07.4`) estão inteiras no resultado (1570 chars, íntegra). **Nenhuma informação perdida — a corrupção do pai 1 é que foi descartada**, o resultado certo |

**`8de3832` é o único achado que é corrupção de verdade, e ela nunca chegou a `master` corrompida:**
o append de `T-07.4` foi inserido NO MEIO do texto da linha anterior (`T-03.6`, `chore`), partindo-a em
`| 2026-09-02T15:00Z | ... em inglês` (296 chars, sem fechar) + o resto do texto original
"vazado" para depois do `]` da linha nova de `T-07.4`. Medido:
`git show 8de3832:docs/INDEX.md | grep -F 'aplicada aqui a `T-03.6`/PR #73' | awk '{print length}'`
→ **296** (linha íntegra em outros commits: **1570**). **Corrigido no commit seguinte da mesma
branch, `90c3b9b`** (`git diff --numstat 90c3b9b^ 90c3b9b -- docs/INDEX.md` → `1 0`, e a linha
volta a **1570** chars) — antes de essa branch alcançar `master`. Mesma classe de defeito narrada
por `T-08.8-builder.md` para `T-08.4-builder` (tooling anterior partindo linha no meio do append),
mas aqui a corrupção passou por um commit intermediário em vez de ser pega antes do commit — e
mesmo assim não sobrevive no histórico de `master`.

São, portanto, **violações reais e não documentadas** da disciplina append-only tal como escrita
— `dad63fe` e `7c068c0` sem perda de informação (texto antigo permanece, riscado ou intacto);
`e92b7bd` e `5e07654` com edição de conteúdo já publicado sem deixar rastro na própria linha.

## Veredito

**Append-only NÃO foi mantido de forma absoluta.** Em 149 commits, 145 respeitam a garantia
(120 de pai único puros + os 3 merges verificados por multiset como reordenação sem perda +
`8de3832`, cuja corrupção morreu on-branch antes de alcançar `master`). **4 commits
(`dad63fe`, `7c068c0`, `e92b7bd`, `5e07654`) reescreveram bytes de uma linha já commitada sem
declarar erratum** — 2 sem perda de informação (tarja/escape), 2 com número antigo
irrecuperável a partir da própria linha (só via `git show <commit>^`). Isso é **achado real**,
não hipótese: nenhum dos 4 está listado em `CLAUDE.md` como exceção documentada, e a task pede
para declarar, não esconder.

**Sem ação corretiva tomada aqui** — corrigir os 4 (voltar `e92b7bd`/`5e07654` a linhas separadas
com erratum, decidir se `dad63fe`/`7c068c0` precisam de tratamento) é decisão de escopo que esta
task, que é auditoria/medição, não tem mandato para executar sozinha; fica nomeado para o
