1. **Engine SQLite, não Postgres/TimescaleDB.** `D6c` só exige "mesmo schema de `md.ingest_run`/
   `md.ingest_gap`" — que hoje é SQLite (`ADR-014/D1`), não Postgres. `backend/pyproject.toml`
   não declara `psycopg`/`sqlalchemy`/`asyncpg` (`grep -nE 'psycopg|asyncpg|sqlalchemy'
   backend/pyproject.toml` → sem match), então `G-A` (`ADR-014/D1e`) não disparou; introduzi-la
   aqui seria essa decisão maior, fora do escopo de "implementar uma fase". Documentado no
   cabeçalho de `sqlite_partition_registry_store.py`.
2. **`FA-3b` como script avulso, real, fora do `pytest`.** Importa `compute_content_hash`
   diretamente do módulo de produção (mesmo código, não reimplementação), roda `compress_chunk`
   e `decompress_chunk` reais contra `timescale/timescaledb:2.17.2-pg15` via docker local, com
   dado sintético rotulado como tal (a propriedade medida é do motor, não de fidelidade de
   mercado — ver docstring do script).
3. **Concorrência (`D6c`: lock consultivo por partição)** — ⚠️ **ERRATUM**: esta linha alegava
   originalmente que o lock de arquivo único do SQLite já era "suficiente". Estava **errado** —
   ver a seção "Correção pós-QA" abaixo, que é a versão vigente desta decisão: o lock real é
   `read_modify_write` (`BEGIN IMMEDIATE`, uma transação cobrindo `get`+decide+`upsert`), não o
   lock de arquivo isolado por `upsert`. Um adaptador Postgres real precisará de
   `pg_advisory_xact_lock` por `PartitionIdentity` quando `G-A` disparar — nomeado, não
   implementado.

## ✅ Correção pós-QA (2026-09-04) — `D6c` "lock consultivo" era comentário, não código

`docs/context/plataforma-dados/gates/T-08.3-qa.md` reprovou o item 3 (`NEEDS_FIX`): a afirmação
acima, "Concorrência coberta hoje pelo lock de arquivo único do SQLite", estava **errada** — o
lock de arquivo do SQLite cobre a transação `upsert` isolada, não a sequência
`get()`→decide→`upsert()` que `record_partition_write`/`record_partition_compaction` faziam em
DUAS conexões/transações separadas. QA plantou
`backend/tests/sentimento/test_partition_registry_concurrency.py`, forçando com
`threading.Event` (determinístico, sem `sleep`) uma corrida write-concorrente-vs-compactação:
resultado medido `(compaction_epoch=1, row_count=1)` em vez de `(1, 2)` — a atualização do write
concorrente perdida em silêncio, 5/5 execuções reproduzem `[MEDIDO pelo QA]`.

**Fix:** `SqlitePartitionRegistryStore.read_modify_write` (novo método,
`backend/src/modules/sentimento/infra/sqlite_partition_registry_store.py:228-286`) abre UMA
conexão, UMA transação, com `BEGIN IMMEDIATE` — que adquire o lock RESERVED do SQLite ANTES do
`SELECT`, não depois do `INSERT OR REPLACE`. Um segundo `BEGIN IMMEDIATE` para o mesmo arquivo
bloqueia (via `timeout=30s` de `sqlite3.connect`) até a primeira transação commitar/reverter —
então o `get`-decide-`upsert` inteiro vira uma unidade atômica por chamador, cobrindo exatamente
a sequência que faltava, não só a metade do `upsert`. `use_cases/maintain_partition_registry.py`
foi reescrito para chamar `store.read_modify_write(identity, mutate)` em vez de `get()` +
`upsert()` separados — as duas funções (`record_partition_write`, `record_partition_compaction`)
não fazem mais nenhuma leitura fora dessa transação única. `get`/`upsert` continuam no store,
sem uso interno deste módulo, para o consumidor read-only de `backtest`/`T-08.4` (`D6c`: "nunca
escreve nele").

**Escopo do lock, declarado (não é o que o comentário anterior alegava):** é um lock **por
arquivo SQLite inteiro** via transação `BEGIN IMMEDIATE`, dentro de um único processo
(`ADR-002/D5`: escritor único) — não um lock por `PartitionIdentity`, e não um lock
entre processos distintos além do que o próprio SQLite já serializa por arquivo. É mais grosso
que o "por partição" que a prosa de `D6c` nomeia, mas fecha exatamente a invariante que `D6c`
pede — nenhuma `compress_chunk` roda com uma escrita da mesma partição em voo — porque hoje há um
único processo escritor e uma única tabela SQLite; um adaptador Postgres real (`G-A`) precisará
de `pg_advisory_xact_lock` por `PartitionIdentity` para a mesma propriedade granular, nomeado no
comentário do módulo (linhas 45-50), não implementado aqui.

**Por que a correção funciona mesmo sem reproduzir artificialmente a ordem do QA:** o teste
plantado força a intercalação via `threading.Event` sobrepondo `get()`/`upsert()` das
subclasses (`_CompactionReaderStore`, `_WriteReaderStore`). Com o fix, nenhuma das duas funções
de uso chama mais `get()`/`upsert()` separados — chamam `read_modify_write`, que faz seu próprio
`SELECT`/`INSERT OR REPLACE` dentro da transação `BEGIN IMMEDIATE`, então os overrides de
`get`/`upsert` do teste não são mais alcançados (os `Event` nunca disparam). O teste passa por
um motivo MAIS forte, não mais fraco: as duas transações completas (`read_modify_write` de
cada thread) são serializadas de ponta a ponta pelo próprio SQLite — qualquer ordem de chegada
produz `(compaction_epoch=1, row_count=2)`, porque `apply_write` preserva o epoch existente e
`apply_compaction` preserva o `row_count` existente, e cada transação lê o estado JÁ COMMITADO
da outra, nunca um estado obsoleto. A asserção do QA (`(1, 2)`, nomeando as duas grandezas) não
foi tocada.
