# T-08.8 — builder: `firing_rate` walk-forward OOS (`ADR-023`)

Componente: `charts` (backend Python, `backend/src/modules/charts/`). Escopo: implementação da
regra de partição/calibração/agregação decidida pelo `quant-architect` em `ADR-023`. Fora deste
despacho, nomeado pela própria ADR: `min_obs`/dispersão de `z` cross-symbol (`T-08.7`,
ortogonal), rota HTTP (`infra`, `T-01.8`), render da legenda OOS (`web`/`charts` TS, gate
`ux-ui-mastery`), calibração walk-forward para `RobustZSpec` (nomeada, não construída).

## O que foi implementado

`backend/src/modules/charts/domain/walk_forward.py` (NOVO):

- `WalkForwardRecipe` — `{spec_version, calib_length_ms, eval_length_ms, step_ms, min_obs_calib,
  min_obs_eval}`, todo eixo estritamente positivo, sem default silencioso na dataclass
  (`ADR-020/D6`). `default_step_ms(eval_length_ms)` é o helper NOMEADO para `D-WF1`'s default
  declarado (`stepMs = evalLengthMs`) — explícito na chamada, nunca implícito no construtor.
- `WalkForwardThresholdRecipe` — `{q, interpolation, op}`, percentile-only, tipo dedicado (não
  reusa `PercentileSpec`, `D-WF3`).
- `to_walk_forward_threshold_recipe(spec: ThresholdSpec)` — narrows `PercentileSpec` para
  `WalkForwardThresholdRecipe` (`window`/`min_obs`/`scope` descartados de propósito); recusa
  `AbsoluteSpec`/`RobustZSpec` com `NonCalibratableSpecError`, citando o tipo pelo nome.
- `WalkForwardFold` + `partition_folds(window, recipe)` — a partição rolante de `D-WF1`,
  `fold(i).calib = [start+i*step, start+i*step+calibLen)`, `fold(i).eval` logo em seguida, sem
  sobreposição entre calib e eval do MESMO fold. `InsufficientWindowForWalkForwardError` antes
  do fold 0 quando `window` não cabe nem um fold.

`backend/src/modules/charts/domain/firing_rate.py` (MODIFICADO, `D-WF5`, emenda a
`ADR-020/D5`): `WalkForwardFiringRate` troca `calib_window`/`eval_window`/`rate` único por
`total_window`/`recipe`/`threshold`/`n_windows`/`excluded_windows`/`rates`/`rate`/`max_rate`.
`__post_init__` agora recusa por CONSTRUÇÃO qualquer inconsistência: `len(rates) != n_windows`,
`rate != statistics.mean(rates)`, `max_rate != max(rates)`, `excluded_windows < 0`, ou qualquer
`rate` individual fora de `[0,1]`. `InSampleFiringRate` **não mudou nenhum campo**. Import
circular evitado com `TYPE_CHECKING` (`walk_forward.py` importa `Window` de `firing_rate.py` em
runtime; `firing_rate.py` importa os dois tipos de `walk_forward.py` só para tipagem).

`backend/src/modules/charts/use_cases/compute_walk_forward_firing_rate.py` (NOVO,
`D-WF6`): segundo ponto de entrada, `compute_firing_rate` (`T-08.6`) **não foi tocado**. Por
fold: lê `calib_values` via a MESMA porta `ObservationSource` (`ADR-020/D7`) com
`knowledge_time_ms = fold.calib_window.end_ms`; abaixo de `min_obs_calib` -> fold EXCLUÍDO
(`D-WF4`) sem ler o eval. Congela `percentile(calib_values, q, interpolation)` num
`AbsoluteSpec` literal (`D-WF3` — `evaluate_scan` nunca recalcula percentil para `AbsoluteSpec`,
garantia por TIPO). Lê `eval_values` com `knowledge_time_ms = fold.eval_window.end_ms`; abaixo
de `min_obs_eval` -> EXCLUÍDO. `evaluate_scan(eval_values, spec=frozen)` dá o `fired_share` do
fold. Todo fold excluído -> `InsufficientWindowForWalkForwardError`.

## Falsificadores provados (não só alegados)

1. **Estrutural (`D-WF1`, aritmético)** —
   `test_walk_forward.py::test_partition_produces_exactly_23_folds_for_the_d8_2_shape`: janela de
   30d, `calibLengthMs=7d`, `evalLengthMs=1d`, `stepMs=1d` -> `len(folds) == 23`, reproduzindo o
   `n=23` que `D8.2`/`PRD-001:649` já publicaram. Mais 5 testes irmãos: folds tocam as bordas da
   janela, evals cobrem o eval-span sem buraco/sobreposição, calibs de folds consecutivos SE
   sobrepõem por desenho, guarda recusa janela curta demais, produz exatamente 1 fold no span
   mínimo.
2. **Anti-lookahead (`D-WF2`)** —
   `test_compute_walk_forward_firing_rate.py::test_each_fold_reads_calib_and_eval_as_of_its_own_fold_boundary`:
   fake porta gravando `(window, knowledge_time_ms)` de cada chamada; sobre 3 folds, prova que
   `knowledge_time_ms` do lado calib é `fold.calib_window.end_ms` e do lado eval é
   `fold.eval_window.end_ms`, DIFERENTE por fold — nunca um valor global repetido.
3. **Anti-tautologia (`D-WF3`)** —
   `test_the_eval_side_is_scored_against_the_frozen_calib_threshold_not_recalibrated`: calib =
   `1..100` (percentil 99 linear congela em `99.01`); eval = `(50,150,250)`. Score CONGELADO ->
   `fired_share = 2/3`. Um bug que recalibrasse `q=99` sobre o próprio eval acharia
   `percentile((50,150,250),99,linear) = 248.0` -> `fired_share = 1/3` — os dois valores são
   longe o bastante (`2/3` vs `1/3`) para o teste reprovar alto se o congelamento for
   contornado. **Este é o caso que a proteção REJEITA**, não só o caso feliz.
4. **Exclusão (`D-WF4`)** — 3 testes: fold abaixo de `min_obs_calib` é excluído E seu eval NUNCA
   é consultado (prova negativa sobre `source.calls`); fold abaixo de `min_obs_eval` é excluído
   depois de ler o calib; todo fold excluído recusa com `InsufficientWindowForWalkForwardError`
   em vez de devolver resultado vazio.
5. **Invariante de agregação (`D-WF5`)** — `test_firing_rate.py`: 6 testes cobrindo
   `n_windows<=0`, `excluded_windows<0`, `len(rates)!=n_windows`, `rate` individual fora de
   `[0,1]`, `rate != mean(rates)`, `max_rate != max(rates)` — todos recusam por construção.
6. **Pipeline completo, `n=23` fim a fim** —
   `test_the_partition_formula_reproduces_d8_2_s_n_23_end_to_end`: fixture achatada (mesma
   população em todo fold) rodada pelo use case inteiro -> `n_windows==23`,
   `excluded_windows==0`, `len(rates)==23`.

## O que NÃO foi reproduzido, e por quê (nomeado, não escondido)

`D8.2` publicou `média 1,404%`, `máx 12,847%` (`q=99`, BTC/30d) e `52×` (`q=99,9`) sobre o
dataset REAL do mercado. **Este builder não reproduz esses três números exatos.** Motivo: o
dataset bruto não está neste repositório (`data/`, gitignored, `CLAUDE.md` "Dado bruto não é
versionado"), e ao contrário do fixture de `D8.1`/`D8.6`
(`tests/helpers/charts_fixtures.py::synthetic_btc_like_population`, que planta APENAS um
escalar — o máximo — sobre uma população SEM eixo de tempo), reproduzir `1,404%`/`12,847%`
exigiria uma série sintética com 30 dias de granularidade cuja distribuição por dia fosse
construída para bater com uma média E um máximo publicados sobre 23 folds reais — isso seria
inventar uma série para casar com uma resposta pré-determinada (curve-fitting do teste), não uma
reconstrução da PROPRIEDADE que `D8.6`/`D8.1` usam como precedente. Optei por provar a
ARITMÉTICA da partição (falsificador 1, que a própria ADR chama de "estrutural, sem precisar do
builder existir") e a CORREÇÃO do mecanismo (2-6) com fixtures honestas, e declarar aqui que a
reprodução literal dos 3 números fica bloqueada por falta do dado real — ver seção Bloqueado.
