## Verificação item a item

**1. Caso "compaction legítima" REALMENTE recusa — CONFIRMADO.**
`backend/tests/sentimento/test_partition_registry_domain.py::test_case_2_compaction_still_refuses_never_accepts_h2_silently`
planta exatamente o cenário: toda partição tocada com `compaction_epoch` maior que o snapshot ⇒
`classify_reproduction_attempt` devolve `ReproductionVerdict.COMPACTION`, e
`enforce_never_silent_number_change` (`domain/partition_registry.py:338-368`) **levanta**
`CompactionReconciliationRequiredError` — nunca devolve `H2` em silêncio. Lido linha a linha,
bate com `D6d` (`ADR-002-motor-de-armazenamento.md:288-294`).

**2. Anomalia distinguível de dado novo — CONFIRMADO, com uma ressalva de escopo do módulo.**
`classify_partition_change` (`domain/partition_registry.py:260-266`) separa `ANOMALY`
(hash mudou, epoch **não** cresceu) de `COMPACTION` (hash mudou, epoch cresceu);
`test_anomaly_wins_over_compaction_when_both_are_touched` prova que uma partição anômala entre
várias compactadas ainda reporta `ANOMALY` — não "principalmente compaction" (`D6d`: "mais
grave"). **Ressalva, não bloqueio:** o ramo "dado novo" (`knowledge_time` diferente) é
explicitamente fora deste módulo por design (`partition_registry.py:19-23`, docstring) — é
`T-08.4`/`backtest` que compara `knowledge_time`. Correto por `D6d` linha 3 da tabela, mas
significa que a distinção "anomalia vs. dado novo" só fecha quando `T-08.4` existir; hoje esta
task cobre exatamente o que `D6c`/`D6d` atribuem a `sentimento`.

**3. `compaction_epoch` só incrementado pelo escritor único, sob concorrência — NEEDS_FIX,
DEFEITO PROVADO.**
`D6c`, literal: *"o escritor único serializa `(escrever, compactar)` por partição com lock
consultivo — nunca uma `compress_chunk` roda enquanto um write ... está em voo"*. Não existe
nenhum lock no código (`grep -n "Lock" backend/src/modules/sentimento/infra/*.py
backend/src/modules/sentimento/use_cases/*.py` — zero ocorrência de implementação, só o
comentário em `sqlite_partition_registry_store.py:21-28` que ALEGA "suficiente" o lock de
arquivo do próprio SQLite). Esse lock cobre a transação de `upsert` isoladamente — não a
sequência `get()`-decide-`upsert()` que `record_partition_write`/`record_partition_compaction`
fazem em duas conexões separadas. Plantei
`backend/tests/sentimento/test_partition_registry_concurrency.py` — força com `threading.Event`
(determinístico, sem `sleep`, 5/5 execuções isoladas reproduzem) o cenário: compaction lê
(epoch=0), write concorrente lê o mesmo estado obsoleto, e o `upsert` que aterrissa por último
sobrescreve o outro. Resultado medido: `(compaction_epoch=1, row_count=1)` em vez de
`(1, 2)` — a atualização do write concorrente é **perdida em silêncio**, sem exceção, sem
detecção. `bash backend/scripts/test.sh` confirma: `1 failed` é este teste.

**5. `partition_key` desacoplado de `chunk_time_interval` — CONFIRMADO.**
`PartitionIdentity.partition_key` (`domain/partition_registry.py:61-84`) é um campo de string
opaco, sem parsing nem derivação de config alguma — `grep -rn "chunk_time_interval"
backend/src backend/tests` só acha o próprio TEXTO da decisão (comentários citando `D6b`), zero
código que leia `chunk_time_interval` para construir `partition_key`. Satisfaz `D6b` por
construção: não há acoplamento porque não há caminho de código que ligue as duas coisas.
