## Por que isto não é decisão de UI a tomar agora (mesmo sob `R9`)

`T-07.14` produz `universe_source` e `deliveryDate`/badge como **dado de saída de uma função TS**
(`frontend/src/app/universe-at.ts`), consumido por quem quer que no futuro construa o dropdown real de
seleção de símbolo em `S2`. Desenhar o badge (glifo, cor, posição) **sem** o componente de dropdown
existir seria o mesmo erro que `T-08.5-design.md` já registrou para `S4`: decidir apresentação visual
antes de o componente-hospedeiro existir, arriscando descarte/reconciliação quando o dropdown real for
desenhado. **Não há decisão de UI real e inevitável aqui.**

**Nota prospectiva, não normativa** (para quem desenhar o dropdown real de `S2` no futuro): quando esse
componente existir, o badge de delisting provavelmente cai na guarda de **procedência/ação/severidade
operacional** (luminância, zero hue) de `ADR-010`, não na guarda de direção de preço nem na de
integridade do dado — mas isso é leitura de agora, sem componente para testar contra
`scripts/verify_screen.py`, e fica com `[NÃO SEI]` explícito até existir tela para auditar.

## O que este gate NÃO pôde auditar, e por quê

Não há `frontend/src/app/universe-at.ts` ainda (`status = "todo"` em `tasks.toml`) — este gate não
audita nomenclatura de código, isso é `ux-audit` pós-`/build`. Não há dropdown real de símbolo em
nenhuma tela — `[NÃO SEI]` se, quando ele for desenhado, o badge proposto acima sobreviverá ao
`design-critique` daquela tela; falsificador: se a tela resultante não convergir com o chrome/paleta já
fixados, é quem desenhar aquele dropdown que escreve esse gate, não uma extensão retroativa deste.
