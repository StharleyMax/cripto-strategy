**Causa raiz, confirmada na fonte, não por suposição:** o seletor `esquery`
`ImportExpression[source.value=/.../ ]` lê o atributo `.value`, que só existe em um nó
`Literal` do ESTree. Um `TemplateLiteral` (com ou sem interpolação) não tem `.value` — tem
`quasis`/`expressions` — e um `BinaryExpression` (concatenação) também não. `esquery` trata
atributo ausente como não-casamento, então a nova regra **nunca é candidata a disparar** para
essas três formas: não é uma falha de regex frouxa, é uma classe inteira de nó AST fora do
alcance do seletor. `require()` é ainda mais estrutural: `no-restricted-imports` **nunca**
registra listener de `CallExpression` — confirmado por `grep -c CallExpression
node_modules/eslint/lib/rules/no-restricted-imports.js` → **0 ocorrências** — então mesmo que o
seletor de `no-restricted-syntax` for estendido, ele teria de ganhar uma regra TOTALMENTE NOVA
(`CallExpression[callee.name="require"]...`) que hoje não existe em nenhum dos dois blocos.

**Por que isto é achado real e não nitpick de laboratório:** `import(`../charts/${x}`)` —
template literal interpolado — é o padrão idiomático de `next/dynamic` quando o componente a
carregar varia por prop/rota (exatamente o cenário que o comentário do próprio builder em
`eslint.config.mjs:125` cita como "a próxima tarefa vai alcançar"); `require()` continua válido
em código que roda sob bundler webpack (Next.js), mesmo com `"type": "module"` no
`package.json` do pacote — a distinção ESM/CJS do Node não se aplica ao código que o bundler do
Next empacota.
