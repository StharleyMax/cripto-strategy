## 3. Pior caso simultâneo — propriedade verificada além dos casos fixos do builder

Fuzz de 2000 amostras aleatórias (`capacity` em `[max, 50*max]`, `n_symbols` em `[0, 2000]`)
sobre `max_symbols_per_partition`/`partition_symbols`/`partition_count` reais: **0 falhas** —
nenhum símbolo perdido (`sum(len(p) for p in parts) == n_symbols` sempre), nenhuma partição
excede `capacity` no pior caso simultâneo (`len(p) * max <= capacity` sempre), e
`len(partition_symbols(...)) == partition_count(...)` sempre. Script em
`/tmp/claude-1002/claude/scratchpad` não persistido (rodado via `python -c`, ver comando na
seção 5).

## 4. Ciclo de correção — confirmado que a versão final NÃO usa a fórmula antiga

Reproduzi a fórmula antiga rejeitada ("1 quente em `max` + resto em `p50`") isoladamente, fora
do código de produção: `n = 1 + (10_000 - 3224) // 21 == 323`; `323 * 3224 == 1_041_352 >
10_000` — confirma que essa fórmula estouraria a capacidade em ~104×, batendo com o relato do
builder. Lendo `max_symbols_per_partition` linha a linha: o único `return` é
`partition_capacity_msg_per_second // throughput.max` — não existe nenhum ramo, default ou
caminho que aplique a fórmula assimétrica. A versão comitada usa `max` simultâneo para TODO
símbolo, sem mistura.
